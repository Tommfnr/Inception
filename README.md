# Inception

## Description

Inception is a system administration project. The goal is to build a small web
infrastructure from scratch, inside a virtual machine, using Docker and Docker
Compose — and to build it **without pulling any ready-made application image**.

The stack serves a WordPress website over HTTPS and is composed of three
services, each isolated in its own container:

| Service | Role | Base image | Reachable on |
|---|---|---|---|
| **nginx** | TLS termination and web server, the single entry point | `alpine:3.23` | `443` (published to the host) |
| **wordpress** | WordPress + php-fpm, no web server of its own | `alpine:3.23` | `9000`, private network only |
| **mariadb** | The database holding the WordPress content | `alpine:3.23` | `3306`, private network only |

Two named volumes make the data survive a container restart: one for the
database, one for the WordPress files. The three containers talk to each other
over a private bridge network, and only NGINX is exposed to the outside world.

```
                                  WWW
                                   │
                                   │ 443  (TLS 1.2 / 1.3)
 ┌─────────────────────────────────┼──────────────────────────────────┐
 │ Virtual machine                 ▼                                  │
 │  ┌──────────────────────────────────────────────────────────────┐  │
 │  │ docker network: inception (bridge)                           │  │
 │  │                                                              │  │
 │  │    ┌─────────┐   3306   ┌───────────┐   9000   ┌───────┐     │  │
 │  │    │ mariadb │◄─────────│ wordpress │◄─────────│ nginx │     │  │
 │  │    └────┬────┘          └─────┬─────┘          └───┬───┘     │  │
 │  └─────────┼─────────────────────┼────────────────────┼─────────┘  │
 │            ▼                     ▼                    ▼            │
 │      ┌──────────┐          ┌───────────────────────────────┐       │
 │      │ db_data  │          │            wp_files           │       │
 │      └──────────┘          └───────────────────────────────┘       │
 │                                                                    │
 │   db_data  -> /home/tfournie/data/mariadb                          │
 │   wp_files -> /home/tfournie/data/wordpress   (shared: nginx + wp) │
 └────────────────────────────────────────────────────────────────────┘
```

The site is reachable at **https://tfournie.42.fr**.

## Project description

### Why Docker here

Each of the three services is described by a `Dockerfile` I wrote myself, built
locally by Docker Compose. Nothing is pulled from Docker Hub except the Alpine
base image, which the subject explicitly allows. No `latest` tag is used
anywhere: the base image is pinned to `alpine:3.23`, and every package is
installed from the distribution repositories at build time.

Every container runs its daemon in the **foreground, as PID 1** — `nginx -g
daemon off;`, `php-fpm83 -F`, `mysqld`. 
If the daemon dies, the container dies, and `restart: always` brings it back. That is the
intended behaviour: a container is a process, not a virtual machine.

### Sources included

```
.
├── Makefile                    # entry point: build, run, clean
├── secrets/                    # passwords, git-ignored, generated by `make`
└── srcs/
    ├── docker-compose.yml      # services, volumes, network, secrets
    ├── .env                    # non-secret configuration, git-ignored
    ├── .env.example            # template, committed
    └── requirements/
        ├── nginx/
        │   ├── Dockerfile      # nginx + openssl, self-signed certificate
        │   └── conf/nginx.conf # TLS, FastCGI pass to wordpress:9000
        ├── wordpress/
        │   ├── Dockerfile      # php83-fpm + wp-cli
        │   ├── conf/www.conf   # php-fpm pool, listens on 9000
        │   └── tools/init.sh   # waits for MariaDB, installs WordPress
        └── mariadb/
            ├── Dockerfile      # mariadb server + client
            ├── conf/my.cnf     # bind-address, port, datadir
            └── tools/init.sh   # bootstraps the database and users
```

### Main design choices

**The startup scripts are idempotent.** Both `init.sh` scripts guard their
one-time setup behind a test — `[ ! -f wp-config.php ]` for WordPress,
`[ ! -d /var/lib/mysql/mysql ]` for MariaDB. On a restart, the volume already
holds the data, the guard fails, and the script goes straight to executing the
daemon. Site content is never wiped by a `docker compose restart`.

**WordPress waits for MariaDB explicitly.** `depends_on` only guarantees start
order, not readiness: MariaDB accepts connections several seconds after its
container starts. The WordPress entrypoint therefore polls `nc -z mariadb 3306`
for up to 60 seconds and exits with an error if the database never answers,
rather than failing obscurely halfway through the installation.

**NGINX and WordPress share the `wp_files` volume.** NGINX does not execute PHP —
it forwards a *path* (`SCRIPT_FILENAME`) over FastCGI to php-fpm. That path must
resolve to the same file in both containers, hence the shared volume. It also
lets NGINX serve the static assets (CSS, JS, images) directly, without going
through PHP at all.

**The TLS certificate is self-signed**, generated at build time by `openssl req
-x509` in the NGINX Dockerfile. Browsers will show a warning on first visit;
this is expected for a local, non-public domain and does not indicate a
misconfiguration. Only TLSv1.2 and TLSv1.3 are accepted.

**Passwords never touch the repository.** `secrets/` and `srcs/.env` are both
git-ignored, and `make` generates the secret files with `openssl rand -hex 16`
if they do not exist. Nothing in a `Dockerfile` contains a password.

### Virtual Machines vs Docker

A virtual machine emulates a full computer: the hypervisor provides virtual
hardware, and a complete guest OS boots on top of it, with its own kernel. That
costs gigabytes of disk, hundreds of megabytes of RAM, and a real boot sequence.

A container shares the host kernel and isolates a process using kernel features
— namespaces (its own view of the filesystem, network, PID tree) and cgroups
(limits on CPU and memory). There is no second kernel and no boot: starting a
container means starting a process. That is why the three services here start in
seconds and why each Alpine image weighs a few dozen megabytes instead of
several gigabytes.

The trade-off is isolation strength. A VM boundary is enforced by the hypervisor
and is far harder to escape; a container boundary is enforced by the host
kernel, so a kernel vulnerability can be a container escape. Containers also
cannot run a different kernel than the host — no Linux containers on a Windows
kernel without a VM underneath.

The two are complementary rather than competing, and this project shows it: the
whole Docker stack runs *inside* a VirtualBox virtual machine.

### Secrets vs Environment Variables

Environment variables carry configuration; Docker secrets carry confidential
values. The distinction matters because an environment variable is far more
exposed than it looks:

- it is visible to anyone who can run `docker inspect` on the container;
- it is inherited by every child process;
- it commonly leaks into logs, crash reports, and `/proc/<pid>/environ`.

A Docker secret is mounted as a file inside the container, at
`/run/secrets/<name>`, on a tmpfs — in memory, never written to the image or to
a layer on disk. It does not show up in `docker inspect`, and it is not
inherited by child processes.

This project applies the split strictly:

| `srcs/.env` (environment) | `secrets/` (Docker secrets) |
|---|---|
| `DOMAIN_NAME`, `WP_URL`, `WP_TITLE` | `db_password.txt` |
| `MYSQL_DATABASE`, `MYSQL_USER` | `db_root_password.txt` |
| `WP_ADMIN_USER`, `WP_ADMIN_EMAIL` | `wp_admin_password.txt` |
| `WP_USER`, `WP_USER_EMAIL` | `wp_user_password.txt` |

The entrypoint scripts read the secrets with `cat /run/secrets/db_password` into
a shell variable, use it, and never export it.

### Docker Network vs Host Network

With `network_mode: host`, a container shares the host's network namespace
directly: no isolation, no separate IP, and every port the container opens is
immediately open on the host. Two containers wanting the same port then
conflict, exactly as two ordinary processes would.

This project uses a **user-defined bridge network** (`inception`), which gives
each container its own network namespace and its own IP address. Two benefits
matter here:

1. **Built-in DNS resolution by service name.** `fastcgi_pass wordpress:9000`
   and `--dbhost=mariadb:3306` work because Docker's embedded resolver maps the
   service name to the container IP. No hardcoded IP address, no `--link` (which
   is deprecated and forbidden by the subject).
2. **Isolation by default.** Ports 9000 and 3306 are reachable *only* from
   inside the network. They are never published to the host, so php-fpm and
   MariaDB are unreachable from outside the VM. Only NGINX declares
   `ports: - "443:443"`, which is what makes it the single entry point the
   subject requires.

`network_mode: host` would defeat both: MariaDB would be exposed on the VM's
port 3306, and the whole notion of a single entry point would collapse.

### Docker Volumes vs Bind Mounts

A container's writable layer is destroyed with the container. Both mechanisms
solve that, differently.

A **bind mount** maps an arbitrary host path into the container
(`/host/path:/container/path`). The host directory is the source of truth: it
must already exist, the host controls its permissions, and Docker knows nothing
about its lifecycle. It is ideal in development, where you want to edit a file
on the host and see the change instantly in the container.

A **named volume** is managed by Docker: created on demand, listed by
`docker volume ls`, removed by `docker volume rm`, and — importantly — its
contents are pre-populated from the image the first time it is mounted. It is
the mechanism intended for persistent application data, because the data is
decoupled from any particular host path.

This project declares two named volumes, `db_data` and `wp_files`, and pins
their storage location to `/home/tfournie/data` as the subject requires, using
the `local` driver's device options:

```yaml
volumes:
  wp_files:
    driver: local
    driver_opts:
      type: none
      o: bind
      device: /home/tfournie/data/wordpress
```

They are addressed by name in the services (`wp_files:/var/www/html`) and appear
in `docker volume ls`, while their bytes land in a predictable directory that
can be inspected from the VM.

## Instructions

### Prerequisites

- A virtual machine running Debian or Alpine
- `docker` and the `docker compose` plugin installed
- `make`
- The domain `tfournie.42.fr` resolving to the local machine:

```bash
echo "127.0.0.1 tfournie.42.fr" | sudo tee -a /etc/hosts
```

### Configuration

The repository does not ship a `.env` file — it is git-ignored, along with
`secrets/`. Create yours from the template:

```bash
cp srcs/.env.example srcs/.env
$EDITOR srcs/.env
```

Fill in every empty value. Two constraints are worth repeating:

- `WP_ADMIN_USER` **must not contain** `admin` or `administrator` in any
  capitalisation — the subject fails the project otherwise.
- Do not append a comment at the end of a value line; keep comments on their own
  lines.

The four password files in `secrets/` do **not** need to be created by hand:
`make` generates any that is missing with `openssl rand -hex 16`.

### Build and run

```bash
make            # generate missing secrets, create the data directories,
                # build the three images and start the stack detached
```

Available targets:

| Target | Effect |
|---|---|
| `make` / `make up` | Build the images and start the stack in the background |
| `make down` | Stop and remove the containers, **keeping** the data |
| `make clean` | `down`, then prune Docker images and build cache |
| `make fclean` | Full reset: containers, volumes, the contents of `/home/tfournie/data`, and images |
| `make re` | `fclean` then `up` — a from-scratch rebuild |

The first run takes a few minutes: the images are compiled, then the WordPress
entrypoint downloads WordPress and installs it. Subsequent starts are immediate,
because the guards in the entrypoint scripts detect the existing data.

### Access

Open **https://tfournie.42.fr** in a browser and accept the self-signed
certificate warning. The administration panel is at
**https://tfournie.42.fr/wp-admin**.

Credentials: the usernames are in `srcs/.env` (`WP_ADMIN_USER`, `WP_USER`), and
the matching passwords are the contents of `secrets/wp_admin_password.txt` and
`secrets/wp_user_password.txt`.

### Verify

```bash
docker compose -f srcs/docker-compose.yml ps       # three containers up
curl -k https://tfournie.42.fr | head              # generated HTML
docker exec -it wordpress wp post list --allow-root
docker exec -it mariadb mariadb -u root -p wordpress -e "SHOW TABLES;"
```

Checking that only TLS 1.2 and 1.3 are accepted:

```bash
curl -k --tlsv1.2 --tls-max 1.2 https://tfournie.42.fr -o /dev/null -s -w "TLS1.2 %{http_code}\n"
curl -k --tlsv1.3            https://tfournie.42.fr -o /dev/null -s -w "TLS1.3 %{http_code}\n"
curl -k --tlsv1.1 --tls-max 1.1 https://tfournie.42.fr    # must fail
```

Data persistence is verified by restarting the stack and confirming the site
still holds its content:

```bash
make down && make up
```

  `ssh.service`. Fixed with `ssh-keygen -A` and `systemctl reset-failed ssh`.
